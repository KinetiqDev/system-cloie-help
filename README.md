# System CLOIE Help Center

The public, user-facing Help Center for **System CLOIE**, the learning outcomes
evaluation platform of Assumption College of Davao.

Live at **<https://help.system-cloie.app>**.

It exists to answer one question for an ordinary user:

> "I am on this page. What am I supposed to do?"

It is **not** developer documentation, a CMS, or a second copy of the technical
manuscript. It is a static Astro + Starlight site: Markdown in, HTML out, hosted
on GitHub Pages.

---

## Stack

| Concern | Choice | Why |
| --- | --- | --- |
| Framework | Astro + Starlight | Navigation, sidebar, TOC, Pagefind search, a11y baseline, responsive docs layout — already solved |
| Content | Markdown / MDX | The source is prose; a CMS would be machinery this site does not need |
| Styling | Plain CSS over Starlight's theme | The System CLOIE design tokens map onto Starlight's `--sl-color-*` interface |
| Search | Pagefind via Starlight | Static index, no search SaaS |
| Deploy | GitHub Pages via GitHub Actions | One static bundle; no server |
| Package manager | pnpm | Matches the main repository |

Deliberately absent: React, Tailwind, shadcn/ui, a database, an API, a client
router, i18n, PWA/service worker, analytics SaaS, a test framework. If one of
these ever looks necessary, prove a stated requirement cannot be met without it
first.

## Local development

```bash
pnpm install
pnpm dev        # http://localhost:4321
```

| Command | Does |
| --- | --- |
| `pnpm dev` | Dev server with hot reload |
| `pnpm check` | `astro check` — TypeScript and Astro diagnostics |


Sidebar order is **deliberate, in `astro.config.mjs`** — not autogenerated. Role
groups are collapsed so the tree stays scannable, and each role's own pages are
the dominant navigation once you are inside one.

Eight roles, no more: Secretary, College Dean, General Education Coordinator,
Program Head, Faculty Member, Student, Alumni, Industry Partner. **Graduating
Student is a condition on a Student account, not a ninth role.**

## Frontmatter

Only fields the site actually consumes.

```yaml
---
title: Publish a Course evaluation
description: Publish a Course-bound evaluation to Students in an assigned Course roster.
role: [faculty]                  # which role(s) this is written for
appRoutes:                       # consumed by the contextual-help resolver
  - /faculty/cilo-evaluations/new
contentStatus: published         # draft | verified | published | retired
productStatus: implemented       # implemented | partial | deferred
lastVerified: 2026-10-04
videoUrl:                        # optional; empty renders a placeholder
videoDuration:
keywords:                        # Pagefind aliases — see below
  - publish evaluation
related:                         # renders the "Where to go next" block
  - /faculty/course-rosters/
---
```

`related` is rendered automatically at the end of the article by
`src/components/MarkdownContent.astro`, so no MDX file has to hand-write the
next-links list.

### Search keywords

`keywords` exists so users find a page using older or informal language. The
prose always uses the current canonical term; the alias lives only in
frontmatter. Do not synonym-cycle inside prose.

Examples already in use: `survey`, `form`, `PLO`, `class list`, `can't submit`,
`403`, `read only`, `roster`.

## Components

Five, all in `src/components/`. There is no general design-system package here.

| Component | Purpose |
| --- | --- |
| `VideoGuide.astro` | YouTube URL → embed + link out; no URL → a quiet "coming soon" slot. Never autoplays. |
| `MediaPlaceholder.astro` | Names the screenshot that belongs there. The page works without it. |
| `AvailabilityNotice.astro` | Used instead of invented steps for deferred features. |
| `RelatedGuides.astro` | The "Where to go next" block, driven by `related`, rendered automatically by `MarkdownContent.astro`. |
| `SiteSearch.astro` | Wraps Starlight's own search control for the homepage. |

A role badge component was considered and cut: the active section is already
visible in the sidebar, the page title already names the role, and the `role`
frontmatter already drives the contextual-help resolver. A badge would have been
a third place carrying the same fact.

## Adding a video later

Set `videoUrl` on the page. Accepts a YouTube watch, share, embed, or Shorts URL,
or a bare video id.

```yaml
videoUrl: https://www.youtube.com/watch?v=dQw4w9WgXcQ
videoDuration: "2:40"
```

Or inline on a page:

```mdx
import VideoGuide from '../../../components/VideoGuide.astro';

<VideoGuide title="Faculty onboarding" duration="5:00" url="" />
```

With a URL it renders a click-to-play iframe plus a **Watch on YouTube** link
(`youtube-nocookie.com`). Without one it renders the placeholder. Written
instructions stay primary either way.

Also update the row in `/videos/`.

## Adding a screenshot later

```mdx
import MediaPlaceholder from '../../../components/MediaPlaceholder.astro';

<MediaPlaceholder caption="Faculty Publish CILO Evaluation page showing the Course assignment picker, the Respondent Preview, and the Publish Evaluation button." />
```

Replace the placeholder with the image once it is captured, and delete the import.
Only add a placeholder where an image would materially help understanding — the
site must remain fully usable without a single screenshot.

## Adding an interface image

Drop the file in `public/` and reference it with a normal Markdown image. Do not
rasterize `cloie-logo.svg`; it is used as a vector in the header and as the
favicon.

## Contextual-help route mapping

Articles declare the application routes they answer via `appRoutes`. `:param`
marks a dynamic segment. Dynamic ids never appear in Help Center URLs.

```yaml
appRoutes:
  - /program-head/programs/:programId/outcomes
  - /program-head/programs/:programId/outcomes/mapping
```

The main application owns the resolver. The contract, implemented in
[`KinetiqDev/system-cloie`](https://github.com/KinetiqDev/system-cloie):

```
application route  →  Help Center route
unknown route in a known role  →  /<role>/
role cannot be resolved  →  /start/choose-your-role/
```

`appRoutes` here is the only coupling. This repository does not ship the
resolver, and the main application does not import this repository.

## Source-of-truth rules

Published content follows this precedence:

1. Current server-enforced application behaviour.
2. Current feature `CONTEXT.md`.
3. Accepted ADRs.
4. Current product documentation.
5. Current user-journey documentation.
6. The Help Center PRD and content architecture.
7. Older manuscript/proposal material.

Rules that follow from it:

- **The application wins.** When a guide and the app disagree, fix the guide.
- **Never write a working guide for a stubbed or deferred feature.** Publish an
  availability explanation instead.
- **Record, do not silently resolve.** Material differences against the planning
  documents live in [`docs/source-reconciliation.md`](docs/source-reconciliation.md).
- **Never invent functionality.**
- **Update `lastVerified`** when you re-verify a workflow page.

A user-facing behaviour change should ask: does it change a label, a required
field, a permission, a workflow step order, a route, a status, a prerequisite, or
an irreversible action? If yes, review the affected Help Center pages.

**Canonical terms:** System CLOIE, Institutional Learning Outcome (ILO), Graduate
Outcome (GO), Course Intended Learning Outcome (CILO), Course, Course assignment,
Course roster, academic period, evaluation tool, evaluation, response,
submission, active role, authorized program. Use the exact UI label the
application shows.

## Deployment

GitHub Pages, built by `.github/workflows/deploy.yml`.

- Canonical URL: `https://help.system-cloie.app`.
- `actions/configure-pages` reports the `base_path` the build must use. The
  workflow forwards it as `SITE_BASE`; with the custom domain it is `/`.
- `SITE_URL` overrides the canonical `site` for pre-cutover builds on the
  project fallback URL.

### Custom domain

The domain is carried in `public/CNAME`, which Astro copies verbatim into the
build output, and registered on the repository through the Pages API
(`cname=help.system-cloie.app`). `actions/configure-pages@v5` no longer accepts a
`cname` input — the file is the supported route.

DNS must point the apex-ish host at GitHub Pages:

| Record | Value |
| --- | --- |
| `CNAME help` | `<owner>.github.io` |
| `A help` | `185.199.108.153` |
| `A help` | `185.199.109.153` |
| `A help` | `185.199.110.153` |
| `A help` | `185.199.111.153` |

GitHub's Pages DNS records are authoritative; confirm against
<https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site>
before changing anything. Enforce HTTPS in **Settings → Pages** once the
certificate provisions.

```

src/
├── assets/cloie-logo.svg     # brand mark (vector, unmodified)
├── components/               # five small Astro components + MarkdownContent
├── content/docs/             # all content
├── styles/
│   ├── tokens.css            # System CLOIE design tokens, light + dark
│   └── theme.css             # maps tokens onto Starlight's --sl-color-*
├── content.config.ts         # docs schema + extended frontmatter
└── env.d.ts
public/brand/                 # acd-logo.png, favicon.svg
docs/                         # PRD, content architecture, reconciliation note
scripts/check-links.mjs       # dependency-free internal link check
```

### Design tokens

`src/styles/tokens.css` is ported from the CLOIE-Blog design system, which is
itself ported from the System CLOIE application. It is the only place a colour,
radius, space, or shadow value may appear. Roles resolve twice — `:root` for
light, `:root[data-theme='dark']` for dark — so no stylesheet branches on the
theme anywhere else.

`src/styles/theme.css` resolves those roles into Starlight's `--sl-color-*`
interface, which is how every built-in Starlight surface (sidebar, TOC, search,
cards, asides, badges, pagination) inherits the brand without re-implementing
any component. Light and dark mode come from Starlight's own theme toggle, which
also respects the OS preference — no custom script.

To change the brand, edit `tokens.css` only.
